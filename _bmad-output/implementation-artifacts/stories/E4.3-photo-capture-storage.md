# E4.3 — Photo capture + reference image storage

> **As Charly,** I want to take 1–3 photos of each object and save them to the catalog, so that the model has visual references when answering Ask queries.

## 1. Context

Catalog reference photos live in `Paths.document/catalog/<object_id>/<n>.jpg`. Unlike the snapshot LRU cache (E2.4), catalog photos are **never evicted** — they persist for the lifetime of the catalog entry. SetupScreen (E4.2) triggers capture; OnboardingService (E4.4) consumes the URIs.

## 4. Technical Approach

### 4.1 Module

`app/src/services/CatalogPhotos.ts`:

```typescript
import { Directory, File, Paths } from 'expo-file-system';
import { captureSnapshot } from '@/adapters/camera';
import { ok, err, type Result } from '@/utils/result';

const ROOT = new Directory(Paths.document, 'catalog');
const MAX_PHOTOS_PER_OBJECT = 3;

export type CatalogPhotoError = 'limit_reached' | 'capture_failed' | 'permission_denied';

function ensureRoot(): void {
  if (!ROOT.exists) ROOT.create({ intermediates: true });
}

function objectDir(objectId: number): Directory {
  return new Directory(ROOT, String(objectId));
}

function listPhotos(objectId: number): File[] {
  const dir = objectDir(objectId);
  if (!dir.exists) return [];
  return (dir.list() as Array<File | Directory>)
    .filter((e): e is File => e instanceof File)
    .sort((a, b) => a.uri.localeCompare(b.uri));
}

export async function captureForObject(objectId: number): Promise<Result<string, CatalogPhotoError>> {
  ensureRoot();
  const dir = objectDir(objectId);
  if (!dir.exists) dir.create({ intermediates: true });

  const existing = listPhotos(objectId);
  if (existing.length >= MAX_PHOTOS_PER_OBJECT) return err('limit_reached');

  const snap = await captureSnapshot();
  if (!snap.ok) {
    return err(snap.error === 'permission_denied' ? 'permission_denied' : 'capture_failed');
  }

  const nextIndex = existing.length + 1;  // 1-based
  const file = new File(dir, `${nextIndex}.jpg`);
  file.write(snap.value.base64, { encoding: 'base64' });
  return ok(file.uri);
}

export async function removeForObject(objectId: number): Promise<void> {
  const dir = objectDir(objectId);
  if (dir.exists) {
    try { dir.delete(); } catch { /* best effort */ }
  }
}

export function listForObject(objectId: number): string[] {
  return listPhotos(objectId).map(f => f.uri);
}
```

### 4.2 SetupScreen integration (from E4.2)

In `ObjectFormSheet.tsx`, the "+ take photo" button calls `CatalogPhotos.captureForObject(currentObjectId)`. When editing an existing object: the objectId is known. When adding a new object: photos can't attach until the object exists in SQLite. The flow becomes:

1. Type display name + (optional) description
2. Tap "Save object" → `OnboardingService.addObject({...})` returns the new ID
3. Now the photo section becomes active — take 1-3 photos via `captureForObject(newId)`
4. Photos linked back via `OnboardingService.updateObject(newId, { reference_image_uri: firstUri })`

Or: enforce "name + description first, photos after creation" as the UX shape. v0.9 keeps it simple.

## 7. Risks

- **expo-file-system File.write base64 mode** — same compat note as E2.4. Verify against installed types.
- **Catalog photos consume real disk** — 3 photos × 10 objects × ~250KB = ~7.5MB. Fine. If Charly ever tags 100 objects, ~75MB still fine.
- **Object ID dependency:** photo capture needs an existing object ID, which only exists after the catalog row is inserted (E4.4). UX in E4.2 must handle the "save object first, then photos" sequencing.
