# E1.8 — `Result<T,E>` type + service skeletons

> **User story:** As a developer, I want a typed `Result` for every service call and empty skeleton files for every domain service, so that later stories slot work into a stable shape and no service throws raw exceptions to the UI.

## 1. Context

XS estimate — the smallest E1 story. Two outcomes: (a) `Result<T, E>` type + helpers exist at a single import path; (b) all six domain services have empty skeleton files with typed signatures so subsequent stories implement *into* them, not *from* them.

If E1.8 lands before E1.3, the TTS adapter uses the real `Result`. If E1.8 lands after, E1.3's local `Result` migrates by find-replace. Sequence is up to the dev agent — but doing this story Day 1 of Sprint 1 minimizes rework.

## 4. Technical Approach

### 4.1 Result type

`app/src/utils/result.ts`:

```typescript
export type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

export const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });
export const err = <E>(error: E): Result<never, E> => ({ ok: false, error });

export const isOk = <T, E>(r: Result<T, E>): r is { ok: true; value: T } => r.ok;
export const isErr = <T, E>(r: Result<T, E>): r is { ok: false; error: E } => !r.ok;
```

Tests cover constructor + predicate + exhaustive-switch behavior.

### 4.2 Service skeletons

Example — `app/src/services/DescribeService.ts`:

```typescript
import { Result } from '@/utils/result';

export type DescribeError = 'low_confidence' | 'network' | 'parse_fail' | 'unknown';
export type DescribeOutcome = { narration: string; objects: Array<{ canonical: string; display: string; room_hint: string | null }> };

export async function run(): Promise<Result<DescribeOutcome, DescribeError>> {
  throw new Error('not_implemented');  // filled by E2.2
}
```

Repeat for each of the six services with their own typed contracts:
- `AskService.run(): Result<AskOutcome, AskError>` (later imports from utterance router).
- `MemoryService.recall(name: string): Result<Sighting | null, never>` (placeholder until E5.2).
- `OnboardingService.getCatalog(): Promise<ObjectCatalog>` and CRUD methods (placeholder until E4.4).
- `HeartbeatService.transition(to: HeartbeatState): void` (placeholder until E2.2 wires it up).

### 4.3 Filesystem skeleton

`app/src/adapters/filesystem.ts`:

```typescript
import { Paths, File, Directory } from 'expo-file-system';
import { CONFIG } from '@/config';

// Snapshot LRU lives at Paths.document/snapshots/ (per architecture §3 AD-5).
// FR-3 catalog reference images at Paths.document/catalog/<object_id>/<n>.jpg.
// All implementations are stubbed in this story; LRU + cache lifecycle land in E2.4.

const SNAPSHOTS_DIR = new Directory(Paths.document, 'snapshots');
const CATALOG_DIR = new Directory(Paths.document, 'catalog');

export async function ensureDirs(): Promise<void> {
  if (!(await SNAPSHOTS_DIR.exists())) await SNAPSHOTS_DIR.create();
  if (!(await CATALOG_DIR.exists())) await CATALOG_DIR.create();
}

// LRU operations (saveSnapshot, evict, etc.) land in E2.4.
```

`expo-file-system`'s new class API is what's used — confirmed in architecture rev 2 patches and in the live npm docs.

## 8. Risks

- **`expo-file-system` API surface drift.** SDK 56 stabilized the new `File` / `Directory` / `Paths` API; if a patch release tweaks names, dev agent adapts per the live docs. The architecture commits to the new API; do not use legacy.
- **Service skeleton over-design.** Resist defining type structures the implementing story doesn't actually want. Each service exports the minimum the consuming story will need; type refinement happens at impl time.
