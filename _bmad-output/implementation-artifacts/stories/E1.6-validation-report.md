### AC1.6.3 — Android implementation

**BLOCKER.** "uses `Vibrator.vibrate(pattern[])` via `expo-haptics` simple impacts AND raw native `Vibrator` for the rhythmic pulse (via `expo-modules-core` if needed, or a thin wrapper)" — this is hand-wavy. `expo-haptics` does NOT expose `Vibrator.vibrate(pattern[])` — that's the Android-native API. The spec is mixing levels. **Fix:** pick one approach explicitly:

- (a) **`react-native-haptic-feedback` for ALL rhythmic patterns on both platforms.** It exposes a pattern API on Android via Vibrator and on iOS via CHHapticEngine.
- (b) **`react-native` core `Vibration.vibrate([pattern])`** for Android rhythmic patterns; `expo-haptics` for one-shots; `react-native-haptic-feedback` for iOS CHHaptic.

Either is fine but the story spec must pick one. **Recommended:** (a) — fewer libraries on the rhythmic path means less surface area to maintain.

### AC1.6.4 — iOS rhythmic via CHHapticEngine

**BLOCKER + NIT.** The §4.2 code uses `setInterval` to fake the rhythm, which the spec itself acknowledges may fail AC1.6.5. That's an honest tradeoff but the AC reads as if CHHapticEngine IS being used. The spec needs alignment:

**Fix:** rewrite AC1.6.4 to be honest about the implementation reality:

> "iOS rhythmic *thinking* pattern: best-effort via `setInterval` of light impacts (CONFIG.HEARTBEAT_THINKING_ON_MS + CONFIG.HEARTBEAT_THINKING_OFF_MS period). If AC1.6.5 perception test fails on Charly's iOS device, escalate to `react-native-haptic-feedback` AHAP pattern player (`trigger('customPattern', { hapticPattern: AHAP_THINKING })`). The AHAP JSON is sideload-tunable."

## 4. Technical Approach

### §4.1 Install

**NIT.** Spec says: "react-native-haptic-feedback is autolinked; if Expo's prebuild is bypassed, add the iOS / Android native config manually per the library README." In SDK 56 with the managed workflow + New Architecture, autolinking requires the library to declare TurboModule compat. **Verify before install:** check the library's New-Arch support badge on its README. If it's CJS-only, expo prebuild + manual native edits are needed (which breaks managed workflow). **Fix:** add an installation pre-check: `npm view react-native-haptic-feedback peerDependencies` and confirm RN 0.85 + NewArch are supported. If not, fall back to RN core `Vibration` + AHAP patterns via custom native module (out of scope for v0.9 — defer rhythmic iOS pulse).

### §4.2 — Implementation code

**BLOCKER.** Per AC1.6.3 above: the Android branch mixes `expo-haptics` impacts with vague `Vibrator.vibrate(pattern[])` comments. Rewrite to use ONE library consistently per pattern type (recommend `react-native-haptic-feedback` for rhythmic on both platforms; `expo-haptics` for one-shots).

Also: the `setTimeout` for the second tap in `answer_ready` uses `CONFIG.HEARTBEAT_ANSWER_READY[0] + CONFIG.HEARTBEAT_ANSWER_READY[1]` (50+100=150ms). That's the gap from first tap start to second tap start, but `impactAsync` is itself ~50ms wide on most devices. So the gap from end-of-first to start-of-second is closer to 100ms — matches the spec's `[50, 100, 50]` pattern. OK.
